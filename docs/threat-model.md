# 威脅模型

本文描述 repo 內的服務與部署配方。審查時比對 PR 變更與對應版本的 [README](../README.md)、[服務入口](../server.py)、[Compose 配方](../compose.yaml)及[資料庫權限](../schema.sql)為準。實際部署如增加代理、外部入口或新身分，需要重新核對信任邊界。

## 要保護的資產

- 逐字稿原文、證據片段、向量、查詢文字與私人來源資訊。
- Bearer token、資料庫 DSN、embedding API 金鑰、部署憑證與備份。
- 證據引用與資料發布版本的完整性，以及唯讀檢索服務的可用性。

## 入口與信任邊界

| 入口或資料流 | 安全假設與控制 |
| --- | --- |
| MCP 用戶端 → Streamable HTTP | HTTP 須通過 Bearer token、Host allowlist 與 Origin 驗證（若提供）。Compose 只將 MCP 埠發佈到主機 loopback，DB 無公開埠。持有 token 的用戶端可讀服務授權的語料，部署方須將 token 限於同一信任範圍。 |
| 本機用戶端 → stdio | stdio 沿用啟動者的本機權限與可讀資料，部署方負責程序與檔案隔離。 |
| MCP → PostgreSQL | MCP 執行期只持有 reader 憑證，使用唯讀查詢。loader 負責入庫與資料版本切換，限於資料庫授予的操作。DDL、角色管理和備份由維護者使用獨立的管理身分處理。 |
| 語料 → 匯入 → 檢索結果 | 語料與檢索結果皆可能含不受信任的內容。回傳保留來源和品質標記，用戶端應將原文視為資料，引用前核對其是否支持主張。 |
| 向量建置／查詢 → 外部 embedding 服務 | 關鍵字檢索預設在本地執行。建置向量可能送出語料，啟用查詢 embedding 後可能送出查詢文字。部署方須先核准外送內容與費用，並限制金鑰可用範圍。 |
| GitHub Actions → 正式部署 | PR 的 CI 使用合成資料。正式部署走 `main` 與 `production` 環境核准，部署憑證只供核准後的工作使用。 |

## PR 安全審查重點

- 確認新增入口與代理保留認證、Host／Origin 驗證和私有網路限制，請求及回傳大小仍有界限。
- 確認讀取、匯入與維護身分的權限分開，切版與回退仍受目前版本檢查及對應的明確操作約束。
- 檢查語料、查詢、向量與憑證是否透過新日誌、錯誤、CI 輸出或外部呼叫跨出授權範圍。
- 修改認證、服務暴露、資料外送或部署權限時，同步核對本文件與變更後的程式。
